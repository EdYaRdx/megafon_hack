# Критический аудит Luna V4

Рабочая база — [локальный бриф](../../docs/contest-brief.md), семь отчётов Luna V4 в [research/product](../product/), отдельный предшествующий отчёт V3, материалы [инфраструктуры](../infrastructure/) и [квалификации](../qualification/), README и `.omp/AGENTS.md`. Аудит использует локальный бриф как поставленную задачу. README и часть квалификационных отчётов описывают прежнюю стадию, когда текста кейса ещё не было. Текущая локальная копия содержит подробные требования. Публичный регламент указывает публикацию партнёрских заданий в кабинете, срок 22 ноября 2026 года в 23:59 МСК и четыре общих критерия. Соответствие текста МегаФона оригиналу и дополнительный бриф для демо остаются **UNKNOWN**. [Регламент, §3.2, §4.1 и §7.4–7.8](https://challenge.mgimo.ai/rules), [публичная страница конкурса](https://challenge.mgimo.ai/).

**Статусы.** `DOCUMENTED` — источник явно описывает правило или свойство. `VERIFIED` — конкретная проверка по исходнику, прямое сопоставление файлов или воспроизводимый расчёт с указанным предметом проверки. `CLAIMED` — сообщение авторов о результате без повторения проверки в этом аудите. `INFERENCE` — обоснованное проектное решение, которое предстоит проверить. `UNKNOWN` — имеющихся данных недостаточно. Статус присваивается утверждению. Так, `VERIFIED` для текста правила не подтверждает работоспособность продукта.

## Существенные выводы и изменения

Например, `skills/` из эскиза требует явного вызова или адаптера, тогда как Cursor и VS Code Local описывают `.agents/skills/`. Другой режим VS Code документирует свой основной путь. Доступ к вебу, разрешения, обнаружение и фактическое применение навыка проверяются отдельно. **DOCUMENTED** для путей, **UNKNOWN** для запуска. | Одна каноническая копия в `.agents/skills/`, документированный явный вход и проверка чистого запуска/нового чата на конкретных версиях. [Cursor](https://cursor.com/docs/skills#skill-directories), [VS Code](https://code.visualstudio.com/docs/agent-customization/agent-skills#skill-locations). |
| **Высокий.** `STATE.md` и append-only JSONL достаточны для продолжения. [Дизайн Luna, Evidence/state/decision schemas](../product/agent-design.md#evidencestatedecision-schemas) | В примере у трёх артефактов нет общего момента публикации. Один писатель предотвращает конкурирующее редактирование, но сам по себе не решает публикацию нескольких файлов. **VERIFIED** отсутствие контракта в эскизе, **INFERENCE** сценарий отказа. | Небольшие полные ревизии, проверка ссылок и единый публикуемый указатель. Тест остановки до и после публикации и сверки повторов. |
| **Высокий.** Источник + локатор + ревизия обеспечивают проверяемость. [Реестр Luna, R04, R05, R07](../product/requirements-and-evidence.md) | Luna верно разделяет цитату и подтверждение. В критериях остаётся проверка выборки локаторов без заранее перечисленных фактов, которые должны повлиять на решение. Источник может быть подлинным, а утверждение — неверно для региона или даты. Несколько перепечаток одного заявления создают видимость независимых источников. Обратные ссылки теряют влияние, если связь изначально пропущена. **INFERENCE** по контрпримерам. | Полностью проверять опоры решения и каждое обещание в малых кейсах. Учитывать охват заранее размеченных фактов, область действия и происхождение. При пересмотре перечитать действующие обещания и пороги дополнительно к обходу ссылок. [ALCE, методика оценки цитат](https://arxiv.org/abs/2305.14627). |
| **Высокий.** Девять задач, три плеча, целевые ≥3 повтора. [План Luna](../product/evaluation-and-roadmap.md#baseline-and-scoring-design) | Полная матрица при трёх повторах даёт 81 базовый прогон до абляций, Luna допускает сокращение. В исходном предложении кейсы описаны, но нет замороженных входов, ожидаемых чисел и порога релиза. Один общий балл смешает качество стратегии, доступ к инструментам и работу при остановке. **VERIFIED** по числу условий и содержанию плана. | Сохранить два сильных baseline, сократить основную матрицу до 18, вынести чистый запуск, перенос и время оператора в самостоятельную проверку. Отдельно проверять развилки, правильные числа и условия обещаний. |
| **Высокий.** Файловый подход, CLI опционален, парсер и вычислитель условны. [Рекомендация Luna](../product/agent-design.md#recommendation) | Чистых файлов достаточно для прототипа и сравнения качества содержания. Аварийная публикация общей ревизии — конкретный риск для продолжения. Маршрут с узким детерминированным `check/publish` делает этот риск проверяемым. Отдельный вычислитель и парсеры имеют смысл при обнаруженном дефекте. **INFERENCE.** | Тонкий файловый контракт с минимальным CLI публикации. Операционная проверка против ручного переноса и вариант без CLI в содержательном тесте, чтобы видеть вклад каждого элемента. |
| **Средний.** Шесть навыков выполняют условие «4–7», а stop нужен при уместности. [Дизайн Luna, Proposed skills](../product/agent-design.md#proposed-skills-6) | **VERIFIED.** Число относится к эскизу в [исследовательском задании Luna V4](../../prompts/overnight-goal-v4.md), тогда как [локальный конкурсный текст](../../docs/contest-brief.md) числа навыков не задаёт. Вводное описание явно называет «закрыть направление», а формальный минимум отдельно фиксирует три альтернативы и статус-кво. | Группировать навыки по моменту использования. Для демо показать и статус-кво, и прекращение направления с последствиями. |
| **Средний.** Стандарт Agent Skills хорош, реализация его валидатора расходится с ASCII-спецификацией. [OSS Luna](../product/open-source-reuse.md) | На проверенной версии текста поле `name` описано словом `unicode`, затем приведены диапазоны `a-z`, `0-9`. Этого недостаточно для категоричного вывода Luna об однозначной ASCII-норме. В качестве переносимого подмножества ASCII подходит. Отдельно подтверждено, что `allowed-tools` экспериментален. **VERIFIED** текст и ограничение. | Использовать безопасное подмножество имён и формат. Разрешения задаются на хосте. Закрепить проверяемую версию перед внешним reuse. [Спецификация, name и allowed-tools](https://agentskills.io/specification#frontmatter), [аудит OSS](open-source-decisions.md). |
| **Средний.** Изученные репозитории подходят как образцы процедур. [OSS Luna](../product/open-source-reuse.md) | Несколько наблюдений Luna сделаны по движущимся веткам. Новая проверка расширяет охват до всех 11 заданных проектов, фиксирует версии, конкретные реализации, лицензии и ограничения. В числе значимых деталей: GPT Researcher может сам заполнять ответы на follow-up в исследованном маршруте, а MoA OptiLLM может заполнить неудавшиеся ответы копией первого результата. Это меняет смысл «уточнений» и «нескольких независимых мнений». | Использовать формат, адаптировать узкие идеи собственной реализацией. Для зависимостей и чужих материалов проверить условия сдачи и конкретные лицензии. Публичное положение §6.2–6.4 описывает отчуждение исключительных прав и коммерческое использование. [Ревизии и локаторы OSS](open-source-decisions.md), [регламент](https://challenge.mgimo.ai/rules). |
| **Средний.** Отдельные аналитики и перекрёстное ревью усиливают качество. История собственных запусков здесь **CLAIMED**, выводы из неё можно проверять по источникам. Даже раздельные контексты могут использовать одну модель и одно ошибочное свидетельство. ## Как менялось решение в ходе аудита

Параллельно работали три реальные исследовательские сессии Codex, отдельно от главного анализа. Они изучали методы, OSS и оценку. Первичные альтернативы и планы формулировались до запроса на критику моей архитектуры. Контексты разделены по задачам, состав моделей и межпровайдерная независимость **UNKNOWN**. Для общих источников искали проверяемое возражение и не голосовали по выводам.

| Вопрос исследователю | Полученное возражение | Изменение |
|---|---|---|
| Методы. Достаточно ли целевого опровергающего поиска и структурного контроля? | Можно получить совпадающие выдержки из зависимых публикаций и пропустить обязательное приложение из-за парсинга. Уверенный тон не сигнал эскалации. | Добавлены происхождение, область действия и семантическая проверка всех ключевых опор. При пропуске прежде проверяется извлечение, затем поиск. |
| OSS. Есть ли обязательная зависимость? | Формат применим без пакета. У MarkItDown теряется контекст workbook/cell, а в Council есть symlink и неполное соответствие маршрутов разных хостов. | В ядре только стандарт и собственный малый CLI. В условиях подключения конвертера — точные локаторы, формулы, единицы и проверка Windows. |
| Оценка. Можно ли приписать выигрыш workflow, если инструмент различается? | Нет равного доступа. Структурная ссылка может быть валидной, а пропущенная связь оставит ошибочное обещание после пересмотра. Пауза между записями выявляет смешанный снимок. | В оценке отдельный matched тест с равным доступом, затем операционный тест полного продукта. В релизных проверках есть зависимость, отсутствующая в явных ссылках, и сохранение незатронутых выводов. |

Альтернативы сохранены в [архитектурном решении](architecture-decision.md). Результат tabletop для контрпримера «действующие условия изменились только в одном регионе» — обязательный пересмотр регионального обещания и сохранение исторического значения в остальных регионах. Это ожидаемое поведение по контракту, проверка агента ещё предстоит. Незакрытые вопросы — подтверждение задания и прав на материалы, реальные хосты/доступы, представительные документы, доступная телеметрия и выигрыш относительно структурированного чата. Для каждого есть критерий и место проверки в [дорожной карте](implementation-roadmap.md).
