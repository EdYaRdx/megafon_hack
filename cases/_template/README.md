# Шаблон продуктового дела

Из корня проекта скопируй `cases/_template/` в новый каталог `cases/<case-id>/`. Копирование создаёт CASE root — папку конкретного дела; это не корень проекта. Заполни brief известными данными и пометь неизвестное. Не помещай сюда секреты и закрытые материалы.

Перед первым запуском и в каждой новой сессии явно укажи агенту активное дело `cases/<case-id>/`. Если путь не указан или неоднозначен, агент должен спросить его и остановиться, а не выбирать дело по соседним папкам или их содержимому.

Все case-файлы и пути внутри них (brief, журналы, state, `ACTIVE.json`, `revisions/` и зависимости) относительны к CASE root `cases/<case-id>/`. Маркер нового протокола имеет полный путь `cases/<case-id>/case-protocol.json`. Общие `AGENTS.md`, `.agents/skills/`, `prompts/` и `references/` остаются относительно корня проекта.

`cases/<case-id>/case-protocol.json` — обязательный явный маркер нового протокола. Сохрани `protocol_id: "checkpoint-v1"`. До первого сохранённого checkpoint состояние `checkpoint_state` равно `UNINITIALIZED`; непосредственно перед записью первого снимка измени его на `CHECKPOINTING`. Отсутствующий, повреждённый или неизвестный маркер нельзя трактовать как legacy. Legacy допустим только для перечисленных в `resume-revise` исторических папок.

- `sources.jsonl` — источники и locators.
- `evidence.jsonl` — извлечённые подтверждения и их ограничения.
- `claims.jsonl` — тезисы, статусы и связи с evidence ID.
- `activity.jsonl` — попытки/результаты, инструменты, ошибки/повторы и доступные время/расходы.
- `approvals.jsonl` — отдельные записи human approval; пустой журнал означает отсутствие approval.
- `state.md` — этап и ссылка на единственную активную полную ревизию.
- Остальные Markdown-файлы — альтернативы, решение, две связанные стратегии и план проверки.

## DRAFT и CHECKPOINTED

Это различие рабочего процесса, не новые значения `checkpoint_state`. Решение владельца, подготовленный документ и опубликованный checkpoint — разные события.
Первый рабочий DRAFT с `UNINITIALIZED` ещё не имеет выбранной ревизии: оставь revision/active-claim control fields пустыми, а рабочие claim IDs укажи отдельно.
Заполняй prospective ID и active set только при финализации шести документов для snapshots, не сразу после выбора направления. До записи первого snapshot установи существующий `CHECKPOINTING`.
Сохрани в `state.md` постоянное условное пояснение из шаблона: control fields описывают содержимое ревизии, а не доказывают её публикацию.
Даже `COMPLETE` manifest и `VALIDATED_CANDIDATE` без настоящего selector и успешного post-selection `classify` не делают дело `CHECKPOINTED`.
При остановке незавершённой подготовки сообщи DRAFT/`INCOMPLETE/CONFLICT` во внешнем receipt/ответе; не дописывай успех и не выбирай ACTIVE. Продолжение подчиняется fail-closed классификации.


## Машинные строки state и decision

Перед копированием snapshots прочитай и сохрани точные имена полей ниже. Это синтаксис `checkpoint-v1`, не свободный пересказ. В корневых файлах и их revision snapshots используй одинаковые значения и порядок claim IDs из manifest. Каждое поле — отдельная строка, без точки, комментария, второго поля или пояснения после значения. Пояснения и условия публикации пиши отдельным абзацем.

`state.md` финализируемого кандидата первой ревизии (prospective ID не доказывает публикацию; сохрани условное пояснение из шаблона):

```markdown
- Case protocol: `checkpoint-v1`
- Active complete revision ID: R0001
- Current claim IDs (active successors only; match manifest): C-001, C-002
```

`decision.md` для той же ревизии:

```markdown
- **Revision:** R0001
- **Active claim IDs:** C-001, C-002
```

Не заменяй эти labels на `Revision ID` или `Active claim IDs` без указанного оформления. Пустой active set записывай как `[]`, не как выдуманный claim. Для первой ревизии `parent_revision_id` в manifest — JSON `null`, без Markdown-поля родителя со строкой `null`. Для следующей ревизии можно добавить отдельную строку `- Parent revision ID: R0001` в state и `- **Parent revision:** R0001` в decision; значение должно совпадать с manifest. Не объединяй родителя с другими полями или прозой.

## Протокол ревизий (один автор записи)

ID ревизии неизменяемы, например `R0001`, `R0002`; в каждом manifest указан ровно один родитель или `null`.
Для ревизии создайте `revisions/<id>/` и сохраните точные копии `options.md`, `decision.md`, `strategy-product.md`, `strategy-communication.md`, `test-plan.md` и `state.md`.
В `manifest.json` укажите ID ревизии и родителя, `status`, явный список `active_claim_ids`, относительный путь и SHA-256 каждого снимка и каждой использованной зависимости решения (входных материалов, неизменяемых снимков источников и нужных журналов).
Не используйте mutable root views, `ACTIVE.json` или несохранённую текущую версию источника как зависимость.
Хэшируйте JSONL-зависимости по точным байтам на момент публикации.

Каждый successor с `parent_revision_id`, отличным от `null`, ОБЯЗАН содержать `parent_manifest_sha256`: SHA-256 точных сохранённых байтов manifest фактического родителя.
Получите байты и digest чтением проверенного файла, не вычисляйте из пересериализованного JSON и не угадывайте.
Root revision может опустить поле или задать `null`, но не фиктивный digest.

Считайте `sources.jsonl`, `evidence.jsonl`, `claims.jsonl`, `activity.jsonl` и `approvals.jsonl` журналами только для добавления: не редактируйте, не удаляйте, не переставляйте и не сериализуйте заново уже записанные строки. Следующая ревизия может добавить новые полные JSON-объекты. Если предыдущий журнал завершался без финального перевода строки, добавьте разделительный перевод строки перед новым объектом; hash всего файла изменится, но прежний префикс байтов сохранится. Исторический hash действителен только если совпадает с точными байтами до границы полного JSON-объекта, включая вариант с завершающим переводом строки и без него. Классификатор применяет это правило только к пяти указанным корневым журналам; изменение или обрезка байтов внутри выбранного префикса приводит к ошибке. Остальные зависимости проверяются по полному hash файла.

Пример структуры manifest (значения SHA-256 должны быть вычислены по сохранённым байтам; пути указаны относительно папки дела):

```json
{
  "revision_id": "R0001",
  "parent_revision_id": null,
  "status": "COMPLETE",
  "active_claim_ids": [],
  "files": [
    {"path": "revisions/R0001/options.md", "sha256": "<computed-sha256>"},
    {"path": "revisions/R0001/decision.md", "sha256": "<computed-sha256>"},
    {"path": "revisions/R0001/strategy-product.md", "sha256": "<computed-sha256>"},
    {"path": "revisions/R0001/strategy-communication.md", "sha256": "<computed-sha256>"},
    {"path": "revisions/R0001/test-plan.md", "sha256": "<computed-sha256>"},
    {"path": "revisions/R0001/state.md", "sha256": "<computed-sha256>"},
    {"path": "input/<decision-dependency>", "sha256": "<computed-sha256>"}
  ]
}
```

Это только иллюстрация формата, а не полная ревизия или допустимое доказательство. Замените примерные пути и значения на полный набор реальных зависимостей и вычисленные хэши. Отдельно вычислите hash окончательных байтов manifest для корневого `ACTIVE.json`; не включайте hash самого manifest внутрь него. `ACTIVE.json` — небольшой изменяемый указатель; он не входит в manifest ревизии.

До gate подготовьте согласованные финальные версии всех шести root views и snapshots: каждая пара должна быть byte-identical, включая options, decision, обе стратегии, test-plan и state.
Зафиксируйте решение, claims, бизнес-обязательства и следующий шаг; не встраивайте transient-текст вроде «ACTIVE старый», «gate NOT RUN» или «не опубликовано» в финальные материалы.
Фактический статус публикации отражают настоящий selector и внешние/append-only receipts.
Сначала сохраните все шесть снимков и подготовьте root views, затем зависимости и manifest; manifest записывайте последним с `COMPLETE` только после проверки полного состава и хэшей.
Корневые `state.md` и `decision.md` обязаны повторять control fields соответствующих snapshots.
Любая используемая зависимость должна быть неизменяемым сохранённым источником/снимком, а не mutable root view или `ACTIVE.json`.

### Журналы только для добавления и исторические хэши

Каждый manifest фиксирует точные байты журналов на момент ревизии. Позднейшие добавленные строки не нарушают checkpoint, если исторический hash совпадает с префиксом текущего файла, заканчивающимся полным JSON-объектом. Hash пустого журнала соответствует нулю исторических строк; будущие записи не относятся к этому checkpoint. Проверка по префиксу допускается только для пяти указанных корневых JSONL. Активные тезисы и решение выбранной ревизии явно указаны в её manifest и снимках; порядок и даты новых строк не выбирают победителя.

Перед созданием первого checkpoint установите `CHECKPOINTING` в `case-protocol.json`, до записи любого снимка ревизии.
Сначала подготовьте согласованные финальные root views и все шесть snapshots (byte-identical), затем проверьте зависимости, manifests и candidate через gate.
Только после успешного gate запишите корневой `ACTIVE.json` последним: он содержит выбранный `revision_id` и SHA-256 точных байтов manifest.
Это изменяемый указатель вне manifest; атомарность замены не предполагается.
Ошибка или прерванная подготовка не разрешает выбирать кандидата: остановитесь со статусом `CONFLICT`, не восстанавливайте последовательность автоматически и не изменяйте историю задним числом.
В финальных state/decision фиксируйте решение, claims и бизнес-обязательства/следующий шаг; не оставляйте утверждения о transient gate/selector, например «ACTIVE — old», «NOT RUN» или «NOT PUBLISHED».
Runtime truth — реальный selector и внешние/append-only receipts.

Пример `ACTIVE.json`:

```json
{"revision_id":"R0001","manifest_sha256":"<sha256-of-complete-manifest-bytes>"}
```

Указатель записывается за пределами набора checkpoint-хэшей, чтобы избежать циклического хэширования. Снимки ревизии не содержат hash указателя.

### Проверка совместимости checkpoint

Формы журналов заданы в [evidence and claim conventions](../../references/evidence-and-claims.md). Локальная проверка хэшей или verifier для отдельного дела не доказывает совместимость с протоколом. **До выбора новой ревизии в настоящем `ACTIVE.json` обязателен штатный pre-selection gate** из developer checkout:

```sh
python tools/case_protocol.py check-candidate /absolute/path/to/case --revision R0001
```

Команда валидирует кандидата относительно фактического выбранного родителя (либо `parent_revision_id: null` для первой ревизии), проверяет точные `parent_manifest_sha256` по сохранённым manifest bytes на каждом ребре всей цепи, snapshots, зависимости, claim prefixes и отсутствие forks, затем вызывает тот же `classify_case` на одной временной копии дела с prospective selector. Все шесть root current views должны быть byte-identical snapshots кандидата. Исходное дело и его selector не меняются. Уже выбранную ту же ревизию разрешено проверять повторно. Единственный успешный результат — `VALIDATED_CANDIDATE` с вычисленными `revision_id` и `manifest_sha256`; это не публикация и не `CHECKPOINTED` исходного дела.

`ACTIVE.json` не может быть зависимостью своего checkpoint ни напрямую, ни через filesystem alias (symlink/hardlink): выбор меняет эти байты. Pre-selection gate отклоняет такие ссылки, а не подменяет их копиями старого selector.

Только после фактического успеха gate запиши эти значения в `ACTIVE.json` последним шагом выбора, без изменения проверенных байтов. Любое изменение зависимостей после receipt требует новой проверки; ошибку/`NOT RUN` нельзя заменять ручным «PASS». После выбора проверь настоящее дело:

```sh
python tools/case_protocol.py classify /absolute/path/to/case
```

Сохрани реальные command/stdout/stderr/exit code обоих вызовов. Только фактический `CHECKPOINTED` разрешает объявить машинную совместимость; exit 0 с `FRESH` недостаточен. До него не выдавай checkpoint за принятый и не продолжай protocol resume.

В staged product workspace модуль `tools/` может отсутствовать: это не разрешение читать вне workspace. Оператор выполняет те же команды в разрешённом developer checkout и возвращает настоящий receipt. Если это недоступно, gate остаётся `NOT RUN`: не выбирай новый checkpoint по предположению. Ошибка означает STOP; не переписывай опубликованные snapshots, manifests или исторические строки ради прохождения. Не создавай альтернативный verifier и не ослабляй consumer.
`classify` сохраняет прежний контракт и может читать checkpoint, чьи старые successor manifests не содержат `parent_manifest_sha256`. Новый pre-selection gate намеренно строже и не может сертифицировать такую историческую цепочку. Не дополняйте задним числом исторические manifests/snapshots и не добавляйте обходной путь; оставьте старые артефакты без изменений.


## Согласование и тезисы

Добавляйте согласования в `approvals.jsonl` отдельно от истории решений/ревизий. Обязательные поля: уникальный ID согласования, кто и на каком основании согласовал, время, точное действие, scope и ограничения, ID ревизии, SHA-256 полного manifest ревизии, тезисы-основания, срок/триггер пересмотра и условия. Изменение ревизии/hash, действия, scope или решающего основания требует нового согласования. Не переносите согласование на другое действие или ревизию. Если полномочия неоднозначны или запись не совпадает, остановитесь (`STOP`). Это договорённость рабочего процесса с участием человека, а не техническое управление правами среды.

Структура записи согласования (один JSON-объект в каждой строке append-only журнала `approvals.jsonl`):

```json
{"approval_id":"A-001","approver":"<name and authority>","approved_at":"<timestamp>","action":"<exact action>","scope":"<limits and included objects>","revision_id":"R0001","manifest_sha256":"<computed-sha256>","basis_claim_ids":[],"expires_at":"<timestamp or NONE>","review_trigger":"<event or date>","conditions":"<conditions or NONE>"}
```

Не копируйте пример согласования в реальное дело и не считайте пустую запись или шаблон согласием.

Поле `supersedes` не выбирает тезис. В полном manifest укажите точные ID активных тезисов и повторите их в текущих `state.md` и `decision.md`. Порядок строк JSONL, даты и принцип «последняя запись побеждает» не должны определять выбор. При неразрешённом ветвлении пометьте вариант `INCOMPLETE/CONFLICT`.

Каждая строка `activity.jsonl` — отдельное JSON-событие. Назначайте отдельный ID и статус результата каждой попытке чтения/запроса источника. Записывайте неудачные попытки записи/редактирования и повторы. Для неизвестного результата или телеметрии указывайте `UNKNOWN`; не дополняйте историю выдуманными событиями.

Для критических расчётов см. `test-plan.md` и `references/metrics.md`. Сохраняйте receipt фактического запуска: точную выполненную команду, рабочую папку, путь и SHA-256 входа, версию инструмента/runtime, exit status, исходные stdout/stderr, результат, единицы, формулу, округление, правила пропусков/ошибок. Неудачная команда остаётся неудачным receipt, а не успешным расчётом. Если инструмент не запускали, укажите `NOT RUN`; не придумывайте команду задним числом.
