## 4. Требования к глубине доказательств

Ориентир для полноценного исследования (если публичные источники реально доступны):

- прочитать и проверить **не менее 15 независимых первоисточников** по профессиональным методикам и архитектуре/evals, с балансом A/B/C/D;
- просмотреть **не менее 8 релевантных открытых репозиториев** дальше README (файлы реализации/примеры/лицензия);
- составить матрицу **всех** обязательных пунктов ТЗ: requirement → решение/инструмент → демонстрация → test/acceptance → риск;
- составить как минимум **3 несовпадающие архитектуры** с одинаковой рубрикой: portability, correctness, cost, user control, time-to-ship, extensibility, failure modes;
- разработать **8–10 разнообразных eval-сценариев** и хотя бы два детальных *мысленных dry-run* на синтетических задачах: падение удержания и запуск/позиционирование нового сервиса. Это проектирование теста, НЕ доказательство выполненного продуктом теста;
- представить зафиксированные независимые позиции A/B/C/D, существенные взаимные возражения и изменившиеся решения.

Это **цели глубины, не стимул выдумывать источники**. Если источник недоступен, отметь UNKNOWN и компенсируй другим действительно проверенным источником. Не делай 15 дублей одной документации и не цитируй поисковые snippets как прочитанный документ.

Для каждого ключевого claim: идентификатор, точный URL/путь/раздел, publisher, дата/версия/дата проверки, что конкретно поддерживается, контрпример или ограничение, тип доказательства `DOCUMENTED / CLAIMED / INFERENCE / HYPOTHESIS / UNKNOWN` (`VERIFIED` — только после реального исполнения соответствующей функции). Для спорных фактов проверь более одного независимого первоисточника при возможности.

## 5. Настоящий Council: независимость, спор, опровержение, пересмотр

Выполни ПОСЛЕ независимых A/B/C/D отчётов, а не имитируй debate одним голосом.

**Раунд 2: Cross-Examination.** Запусти отдельные read-only задания с выдержками конкретных чужих CLAIM IDs:
- A проверяет реальную пользу и стоимость конструкции C и предлагает simpler counter-design.
- B проверяет утверждения A на совместимость с доказуемыми коммуникационными обещаниями.
- C оспаривает техническую/операционную реализуемость рекомендаций A/B.
- D проверяет оценимость общих заявлений, возможные benchmark leakages и ложные PASS.
Попроси **не менее шести конкретных возражений по делу в сумме**, каждое с исходной цитатой claim, контрдоказательством/проверяемым тестом, severity и вердиктом. Нет новых данных → не размножай одинаковые возражения.

**Раунд 3: Adversarial Review.** Новый `reviewer` с чистой постановкой задачи (без сообщения «первый вариант уже хороший») должен попытаться опровергнуть recommended architecture, проверить полноту ТЗ, license risk, скрытые зависимости/paid APIs, воспроизводимость, недостающие сценарии и feasibility до дедлайна. Отчёт ревьюера — независимый контекст, но **та же модельная семья**, не называй это multivendor proof.

**Раунд 4: Targeted Revision.** Верни авторам только относящиеся к ним существенные дефекты. Для каждого укажи `ACCEPTED / REJECTED_WITH_EVIDENCE / UNRESOLVED`, изменилось ли решение и почему. Допускается второй проход только при новом evidence или критической ошибке. Lead собирает разногласия вместо голосования моделей. Нет consensus ≠ fail при честно сформулированном эксперименте.

**Раунд 5: Decision Gate.** Сверь итог с конкурсным brief и критериями глубины из раздела 4. При незакрытых блокерах отдели решения, которые можно принять сейчас, от тех, для которых нужен demo brief или тест. **Ни один агент не проверяет свой собственный окончательный deliverable в одиночку**; принятые решения должны опираться на независимые тестовые критерии/проверенные источники.

## 6. Архитектурный результат, который нужен утром

Выдай не абстрактные идеи, а структуру продукта (приземлённый MVP, а не на 6 месяцев):

1. Выбранная архитектура агента и 2 альтернативы: что отказались делать и почему; зависимости / список нужных файлов, skills, scripts и минимум условий запуска.
2. Workflow `intake → plan → evidence → options → critique → decision → product+comms → experiment → state → resume/revise`, точки обязательного human choice, graceful degradation.
3. Минимальные строгие *schemas* для `case-state`, `evidence`, `claim`, `assumption`, `option`, `strategy`, `decision`, `experiment`, `change-impact` с 1–2 короткими примерами и правилами invalidation/freshness. Избегай собственной БД, если это не доказано нужным.
4. Конкретные 4–7 будущих `SKILL.md`, не 30. Для каждого: trigger, входы, outputs, проверка, какой внешний готовый skill можно адаптировать.
5. Способ работы с документами, таблицами, сайтами: минимальный tool chain, повторяемые расчёты и точная цепочка происхождения фактов.
6. Согласование product strategy и communications strategy, включая обещания, которые нельзя делать без evidence.
7. `new chat` continuation procedure (checkpoint сохраняется в файлах продукта), decision-revision при новых данных, failure handling/idempotence.
8. Evals + baseline: задачи, scoring, blind review, hard negative cases, инструменты, time/usage/cost logging; отсутствие ложных VERIFIED.
9. Demonstration plan: что покажет видео ≤10 минут, в том числе остановка/новый чат; подготовка публичного demo case после публикации официального дополнительного брифа.
10. **План разработки на оставшееся время**: Day-1 MVP первый vertical slice; Day-2 eval-driven correction; затем переносимость, изменение данных, демонстрация, запись видео, отчёт, буфер. Каждая задача с scope, observable DONE и зависимостями, без работы ради инфраструктуры.

## 7. Независимый стресс-тест дизайна (без реализации)

На синтетическом запросе о падении удержания и на запросе о запуске нового цифрового сервиса выполни два проектных walkthrough:

## 9. Структура итогового результата (только ответ, read-only режим)

Финальный ответ должен быть **самодостаточным** и пригодным для сохранения утром. Секция за секцией:

1. `STATUS` — FULL/PARTIAL, реально выполненные раунды, agent IDs, source/repo counts, ограничения.
2. `EXECUTIVE DECISION` — выбранная архитектура, ключевая причина, strongest counterargument и критерий пересмотра.
3. `REQUIREMENTS MATRIX` — все обязательные пункты, демонстрация и независимый AC.
4. `PRODUCT + COMMUNICATION METHODS` — проверенные методы и ожидаемые процедуры.
5. `OPEN-SOURCE REUSE MATRIX` — конкретные checked code/example/license locations, вердикт.
6. `ARCHITECTURE COMPARISON` — 3 варианта, tradeoffs, выбранные skills/scripts/data layout, state/resume.
7. `AGENT DEBATE TRANSCRIPT SUMMARY` — отдельные initial positions, CLAIM-ID возражения, что изменилось после ревью, остающиеся разногласия, `agent://` или `history://` IDs для подлинных сессий.
8. `DESIGN DRY-RUNS` — 2 сценария и выводы о failure modes.
9. `EVAL + BASELINE PLAN` — 8–10 cases, metrics, review, cost/time, failure conditions.
10. `IMPLEMENTATION ROADMAP` — первые два вертикальных среза, задачи до 22 ноября, чего не делать.
11. `SOURCE REGISTER` — хотя бы самые влиятельные независимые проверенные источники с точными ссылками, датами, применимостью и claim IDs.
12. `UNKNOWNS / BLOCKERS / NEXT DECISIONS` — что нужно от человека и официального demo-brief.

Только публичные данные, без установки и изменения файлов проекта. Результат данного read-only процесса должен быть ПОЛНЫМ самостоятельным Markdown-отчётом в последнем ответе, а не краткой отпиской: внешний launcher сохранит именно этот ответ в `research/product/overnight-research-v3.md` и при успешном завершении создаст коммит в отдельной Git-ветке для утреннего ревью. Проверенные источники и существенные разногласия обязательно включай в финальный текст, потому что именно он будет сохранён и опубликован.
