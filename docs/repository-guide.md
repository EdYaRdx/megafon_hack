# Карта репозитория и решение по составу

**Срез:** `main` после PR #26, 20 ноября 2026 года. Эта страница описывает **текущий фактический состав и границы**, а не предлагает переписать протокол хранения дел ради чистой витрины.

## Принцип организации: два уровня чтения

**Первый экран (для Product Owner и жюри):** [README](../README.md) → [демонстрационный сценарий](contest-demo.md) → [две стратегии](../cases/mobile-product-strategy-demo/) → [Quick Start](quickstart.md).

**Углубление (для разработчика и аудитора):** [архитектура](architecture.md) → `AGENTS.md` / Skills / references → [шаблон и протокол](../cases/_template/README.md) → [evaluation](evaluation.md) → [исторические исследования](../research/README.md).

Репозиторий — **продуктовый файловый агент**, а не единый контейнер для всех вспомогательных AI-инструментов, исследовательских стендов и персональных рабочих сессий.

## Keep / present / archive / do not ship

| Группа | Действие сейчас | Почему |
|---|---|---|
| `AGENTS.md`, `.agents/skills/`, `references/` | **Оставить в основном репозитории и поставке** | Это продукт; без них кодовый ассистент не получает нужный процесс |
| `cases/_template/` и `tools/case_protocol.py` | **Оставить** | Структура нового дела и реальные checkpoint gates |
| `tools/`, `tests/`, `.github/workflows/` | **Оставить** | Воспроизводимость, диагностика и автоматическая проверка |
| `cases/mobile-product-strategy-demo/` | **Оставить целиком до решения о правах на PDF** | D0001–D0003, manifests, зависимости, receipts и черновики — связанная цепочка; удаление PNG/логов может нарушить хэши |
| `cases/pantrypath-week4-20261115/` | **Оставить как дополнительный пример** | Демонстрирует другой домен без телеком-специфики; не второй главный конкурсный сюжет |
| Остальные `cases/*` | **Не удалять в этом релизе**, маркировать в [каталоге](../cases/README.md) | Часть — фикстуры для аудита и исторические сценарии; удаление требует проверки ссылок и тестов |
| `docs/quickstart.md`, `docs/architecture.md`, `docs/contest-demo.md` | **На первом уровне навигации** | Это пользовательский путь: начать, понять, проверить |
| `docs/release/`, `docs/*handoff*`, `docs/research-plan.md` | **Оставить как датированный архив, не рекламировать в README** | Хранят исторические выводы/границы; не всегда отражают HEAD |
| `research/` и `MGIMO_RESEARCH_TO_IMPLEMENTATION.md` | **Архивировать логически (оставить на прежних путях)** | Полезны для provenance, но не являются инструкцией запуска |
| `.omp/`, `START-OVERNIGHT-V3.txt`, `start-overnight-product-research-v3.cmd`, `prompts/overnight-*` | **Не использовать в runtime или публичном quickstart** | Это development-инфраструктура; физический перенос требует проверки старых ссылок и зависимостей |
| Локальные `.env`, токены, raw Codex/OMP transcripts, host paths | **Не добавлять в Git** | Приватность; сохранение `UNKNOWN` предпочтительнее ложных утверждений о затратах |
| Синтетические рекламные скриншоты, неподтверждённые badges | **Не добавлять** | Визуальное оформление не должно вводить жюри в заблуждение |

**Почему пока не переносим целые каталоги:** в файлах существующих дел есть абсолютные и относительные ссылки, SHA-256 зависимости, исторические locators и проверки. Перемещение ради косметики повышает риск регрессии и не облегчает основной путь, если README и навигация уже ведут к продукту. Физическое выделение архива — отдельное изменение после карты зависимостей и тестов.

## Связанные, но отдельные проекты

| Проект или направление | Что можно использовать | Почему не переносим его код |
|---|---|---|
| **Deep_research_CLI / OptiLLM / Polza** | Методологию provenance, бюджетных оговорок и review; только подтверждённые выводы через ссылки в reports | Платная исследовательская обвязка, токены и proxy **не являются runtime-зависимостью** этого агента; учёт стоимости внутренних вызовов может быть `UNKNOWN` |
| **OMP** | Датированные отчёты разработки, independent review и результаты release-checks | OMP создавал и проверял репозиторий; пользовательскому агенту он не нужен |
| **Agent Platform / DSH** | Идеи строгого разделения роли автора, проверки и разрешений | Полноценный control-plane и SQLite runtime решают другую задачу; ТЗ просит папку агента, не автономную платформу |
| **mgimo-omp-docker / локальные worktrees** | Инструкции проверки из clean host после независимого подтверждения | Содержат локальные окружения, историю испытаний и потенциально машинные пути |
| **Council / OpenClaw / OpenHands / внешние MCP** | Точечные идеи independent review и инструментальной интеграции | Не проверены как необходимые дополнительные runtime-компоненты; новые зависимости не окупаются без измеренной пользы |

Это **границы интеграции**, не заявление, что все перечисленные системы успешно работали в конкурсном E2E. Сопутствующие репозитории имеют собственные лицензии, настройки, расходы и безопасность. Не копируйте их API-ключи, configs, результаты запуска или README целиком.

## Рекомендуемый состав передачи жюри

**Передавать после разрешения прав:** текущую проверенную версию продукта (инструкции, Skills, references, tools, tests, template), основной обезличенный кейс целиком, README/Quick Start/architecture/demo/description/evaluation, видео и фактическое описание расходов. Панель разработки и устаревшие операционные отчёты не обязательны для первого ознакомления.

**Не передавать:** Git history с личными путями, исходное приватное дело R0001–R0003, raw sessions, локальные конфигурации моделей, секреты и внутренние неразрешённые материалы. Исходные R-ревизии нельзя просто объявить эквивалентом D-копии; историю преобразования объясняет [EXPORT.md](../cases/mobile-product-strategy-demo/EXPORT.md).

Текущий репозиторий оставлять **PRIVATE**. После решения о правах на `Пример брифа.pdf` допустимая передача — ZIP текущего согласованного дерева **без `.git`** или новый проверенный history-free репозиторий. Не делать существующую историю PUBLIC. Лицензию и доступ жюри определить отдельно; пустое поле лицензии не означает permission to redistribute.

## Контроль перед финальной публикацией

1. Сверить PDF-образец с актуальным файлом и требованиями в личном кабинете MGIMO, подтвердить право передачи документа и производных материалов.
2. Пройти [checklist подачи](submission-checklist.md) и [release verification](release/contest-rc-verification.md).
3. Проверить пути/ссылки и tests на финальной копии; отдельно проверить реальное открытие в выбранном host и `RESUME CASE`.
4. Добавить **настоящие** скриншоты и видео только после приватной проверки (см. [media guide](demo-media-guide.md)).
5. Для GitHub вручную задать краткое описание, аккуратные topics и лицензирование **только после решения владельца прав**.

Любые изменения опубликованных `D0001–D0003` должны проходить существующий протокол; документационный PR не меняет их байты.
